# Typed Math terminal storage and character extraction

This static continuation follows the actual 138D → 1F44 → 1F41 ownership chain into MyScript2D.dll. It closes a suspected name/character lookup boundary as storage access, not a missing learned model or grammar. It adds no runtime code, model mapping, source mutator or application switch. The audit pins eighteen complete contiguous Ghidra bodies, ten exact straight-line return leaves, 268 instruction locations and four metadata/data regions. It composes the preceding public builder and Document route audits. Vendor DLLs were only read; the new Ghidra project is on E.

## Concrete owner and method bindings

The Math 138D class descriptor derives from 1F44; the actual 1F44 descriptor is in MyScript2D at 088130 and derives from 1F41. Its primary table at 088180 names destructor 005820, the actual descriptor, and the result-access methods. Primary +30 binds to 0059C0. Constructor metadata at 0880E0/0880E8 binds the deep-copy constructor 0053B0 and the separate 005730 constructor. These exact relationships are checked from binary tables.

Math 040C40/040CC0 through 040E40 resolve the real 1F44 base service and forward the inherited operations. For example, 040DA0 forwards base +30. Math 040E80 also resolves that same base +30 operation, receives its supplied candidate string, obtains its byte length through the actual engine string service, and appends those bytes through 0029A0. This is actual data access through the retained object, not a cast from an AL symbol string to a typed terminal.

The public ABI callback table for interface 13F0, proved in the previous batch, remains distinct from these native base adapters. The storage/access evidence here does not assume that adjacent public wrapper addresses implement native V50/V68. It pins the actual calls and the actual base method table instead.

## The supplied result has owned bytes and structured records

0053B0 initializes base 1F41 and copies already supplied data into the new 1F44 owner. The source and destination contain a byte-vector header at +10, a scalar at +20, 12-byte metadata-vector headers at +28 and +38, and an owned array at +48 with count +50 and capacity +54. The array element stride is 0x28. Each such candidate owns a byte-vector header, two float fields at +10/+14, and a nested array at +18 with count/capacity +20/+24. Nested element stride is 0x38 and includes a byte vector, two 12-byte metadata-vector headers, and trailing flags at +30/+34. The constructor copies the supplied trailing owner flags at +58/+5A/+5C. These values are supplied result state, not newly inferred scores or positions.

The allocator strides resolve misleading decompiler array types: 004470 appends **bytes**, reserves count+1 capacity and copies count bytes; 004280 appends **12-byte elements** and copies count×12 bytes. Their `undefined1[32]` decompiler pointer notation does not mean a 32-byte element. Both use the pinned growth factor 1.5. A reserved extra byte is not evidence that these append helpers themselves write a terminator; their complete bodies do not do so. String conversion/termination belongs to the separately called string service.

0053B0 zero-initializes newly allocated nested arrays before filling them, maintains the relevant owned counts, and reaches the object's destructor on failed construction after base initialization. It does not roll back an external page. 005820 frees the outer name bytes, each candidate name, every nested symbol's bytes and two metadata buffers, each nested array, the candidate array, the owner's two metadata buffers and finally the actual 1F41 base. No existing borrowed input array is silently adopted as the deep-copy output.

005730 is a **different constructor**, accepting a parameter size of 0x20. It initializes the base, appends supplied name bytes, assigns the supplied scalar and metadata headers/scalars, starts with no candidate array, and sets trailing defaults including a 0xFFFF field. This must not be described as another cleanup function, nor treated as interchangeable with the deep-copy constructor. Transferred header ownership and all callers of that constructor require their own provenance proof before any runtime port; this batch does not admit arbitrary caller-supplied headers.

## Character extraction does not infer the expression

2D 0059C0 locates an existing candidate by the actual 0x28 stride and asks engine string service 5, V40 for that candidate's byte string. 004910 similarly accesses the owner's supplied name. Exact getter leaves expose the actual metadata count, one 12-byte metadata element, candidate count, selected scalar and two supplied float fields. The nested accessor uses the existing 0x28 candidate and 0x38 symbol arrays. No matrix inference, token classification, alternative search or structural grammar appears in these complete scoped routines.

Math 040F10 reads the nested symbol count from the selected candidate's +20. 040F90 reads the already stored symbol at candidate +18 with 0x38 stride, converts its name through the same string service, obtains its byte length and appends bytes via 0029A0. The exact 041020/041040 leaves read the nested metadata count and copy one actual 12-byte element. The 040F20 routine constructs a separate 1394 object from the retained owner and supplied candidate/symbol indices; it does not manufacture a semantic node name.

The complete Math 0029A0 helper is a byte-vector append: grow with stride 1 and count+1 reserve, zero or copy exactly the supplied bytes, update count and return status. It has no label dictionary, Unicode category grammar, fraction parser or superscript parser. Its presence after a typed terminal name operation must not be counted as recovery of a neural semantic stage. Decompiler `void` prototypes on forwarding helpers are not used to claim that native ABI status or allocation failures are ignored; the consumer's calling convention and subsequent status checks remain material.

The Document 058420/0590C0 consumers from the previous batch therefore read real selected candidate/symbol state and source selections that already exist. They do not explain how newer EE4 markup should be transformed into those old objects. Likewise the public ED9 MathResultBuilder accepts supplied names, text and selections and can create real DOM, but its typed events are another input protocol. Neither positive result justifies inventing a hidden EE4-to-138D bridge.

## Scope for subsequent work

The concrete next boundary is the **producer of the supplied typed candidate arrays and constructor arguments**, together with full interface-registration and generic allocation provenance. This batch does not recover that producer, a full 2D recognition grammar, every 1F41 method, a native semantic confidence measure or any linkage from cold EE4 alternatives to these constructors. No runtime storage port is requested here merely to reproduce already supplied arrays.

For the application, the existing strict experimental structural adapter remains explicitly independent glue over actual cold first EE4 output. The actual neural corpus and its range/score evidence remain unchanged. This storage proof provides no reason to calibrate confidence as 1, select a secondary candidate by its expected label, claim Russian recognition complete, or announce that the whole SDK engine has been transferred.
