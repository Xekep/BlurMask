Проверка 28 октября 2026 года: в `tools/handwriting` находятся 475 Python-файлов,
во всём `tools` — 1323 (включая два новых инструмента). Статический анализ нашёл
141 Python-файл с несколькими потребителями. Это карта ссылок, а не число
дублирующихся запусков и не процент готовности движка. Скорость переноса пока
не измерялась; обещать коэффициент ускорения на этих данных нельзя.

## Уже добавлено

`tools/handwriting/plan_port_checks.py` читает Python через AST, не импортируя
его и не запуская ни проверяемый код, ни исходный движок. Он сохраняет SHA256
скриптов, строки с файловыми ссылками, неоднозначные ссылки, ошибки синтаксиса,
общих потребителей и транзитивный список потенциально затронутых скриптов.
Циклы ссылок допускаются и не приводят к бесконечному обходу.

Пример из корня репозитория (нужен Python 3.10+):

```powershell
python -B tools/handwriting/plan_port_checks.py `
  --output .artifacts/port-impact.json `
  --changed src/InkRecognition/LegacyFreshMainGlobalWordTextPublication.cs
python -B tools/handwriting/test_plan_port_checks.py
```

Выходной файл должен быть новым: существующее доказательство не перезаписывается.
Для указанного исходника сейчас найдены три кандидата: runtime-аудитор WordText,
source bridge и compile-default reader. Это НЕ полный набор проверок: исходники
также подключаются через каталоги, glob и проекты сборки. Такие зависимости,
вычисляемые пути и внешние captures текущий скрипт не восстанавливает. Его вывод
предназначен для просмотра; автоматически запускать или исключать тесты по нему
нельзя. Наличие ссылки также не доказывает вызов subprocess.

Проверены транзитивное распространение, цикл, неоднозначные одинаковые имена,
точный путь, игнорирование комментариев, изменение хеша и ошибка синтаксиса.
Реальный проход завершён без ошибок разбора всех 1323 файлов.

## Следующие полезные скрипты в порядке внедрения

Первые два пункта теперь имеют начальную реализацию: см. раздел исполнителя ниже.
Расширение на сборки и model inference ещё не выполнено. Следующим шагом добавлен
[пакетный статический экспорт Ghidra](batch-function-export.md) с проверкой
исходных байтов; эта разработка идёт отдельно от выпущенного тега 1.2.8.

1. **Явный реестр проверок.** Для каждого шага записать argv, рабочий каталог,
   входы, выходы, timeout и предшественников. Полученную карту использовать для
   первоначального заполнения, затем проверить вручную. Действующие аудиторы
   имеют разные CLI и иногда сами запускают подшаги; универсально вызывать их
   по имени небезопасно для достоверности результата.
2. **Измеряемый исполнитель с кэшем.** Сначала сохранить время каждого шага и
   число повторных вызовов. Ключ включает хеши всех транзитивных входов, моделей,
   PE, скриптов, исходников, фактически собранных DLL/PDB, argv, конфигурации,
   SDK/runtime и значимых переменных окружения. При неполном перечне входов кэш
   выключен. Хеш исходного Python-файла сам по себе недостаточен. Проверять
   целостность выходов; не кэшировать ошибку, timeout или частичный отчёт.
   Сначала сравнить холодный, повторный и запуск после изменения каждого типа
   входа. Не менять PDB/source gates ради попадания в кэш.
3. **Пакетный статический экспорт Ghidra.** Принимать список адресов, объединять
   нужные функции и ссылки в один headless-сеанс существующего проекта. Хранить
   хеш бинарника, версию Ghidra, параметры анализа и хеш экспортирующего скрипта.
   Повторно экспортировать изменённый набор, сохраняя старый как доказательство.
   Это экономит запуск анализатора и ручное извлечение, но не восстанавливает
   автоматически типы, владение объектами или косвенные вызовы.
4. **Генератор каркаса переноса.** Из явного описания структуры создавать C#
   layout, чтение полей, граничные fixtures и заготовку независимого аудитора.
   Сложные алгоритмы оставлять явными незавершёнными шагами. Одинаково
   сгенерированные реализация и oracle не являются независимой проверкой.
5. **Единый прогон реальных записей.** Сначала завершить все captures без доступа
   к ответам, затем оценить текст, геометрию, время, память и причины отказов.
   Сравнивать с закреплённым baseline; отдельно показывать изменение admission
   policy и изменение самого распознавания. Качество русского/английского
   слитного почерка нельзя установить по числу перенесённых функций.

Общий запуск больших сборок и recognition-процессов должен иметь ограничение
параллельности и памяти: конкурирующие сборки могут замедлить работу. Сначала
полезнее убрать доказанные повторные шаги и повторную подготовку неизменных
данных, затем измерять пользу параллельности.

Автоматический перевод всего декомпилированного C в C# сейчас не предлагается:
неустановленные указатели, размеры структур, float-порядок, callbacks и жизненный
цикл владельцев требуют проверки по инструкциям и исходным данным. Скрипты
могут ускорить сбор доказательств и повторные проверки; они не заменяют эти
оставшиеся работы. В рамках этой проверки перенос алгоритмов не возобновлялся,
production-код и выпущенный RC не изменялись.

## Исполнитель явных проверок

Добавлен `tools/handwriting/run_port_checks.py` и проверенный начальный профиль
`tools/handwriting/port-checks-static.json`. Профиль запускает тесты карты ссылок
и существующие побайтовые/негативные проверки ресурсов experimental AUTO.
Все локальные импорты экспортёров, ресурс и два потребляемых исходника приложения
указаны в его входах. Распознавание и vendor DLL не запускаются.

```powershell
python -B tools/handwriting/test_run_port_checks.py
python -B tools/handwriting/run_port_checks.py `
  tools/handwriting/port-checks-static.json `
  --output .artifacts/port-run-001 `
  --cache .artifacts/port-cache
# Для повторного запуска укажите новый output, сохранив тот же cache.
# --no-cache принудительно выполняет шаги, не читая и не записывая кэш.
```

Исполнитель поддерживает только явные Python-команды. В профиле каждого шага:

- `id`, `argv`, `inputs` — имя, массив аргументов без shell и файлы/шаблоны входов;
- `outputs` — обязательные файлы относительно каталога шага;
- `dependsOn` — имена предшественников, топологическая сортировка и отказ на циклах;
- `timeoutSeconds` — предел от 0 до 600 секунд, не включая 0;
- `cache` — разрешение кэша, только вместе с проверенным вручную `inputsComplete=true`.

Подстановки `{python}`, `{root}`, `{out}` обозначают текущий интерпретатор,
репозиторий и новый каталог шага. Каждый шаблон входов должен найти хотя бы один
файл; изменение состава glob тоже меняет ключ. Каталоги `bin`, `obj` и
`__pycache__` исключены. Поэтому сборки DLL/PDB этот механизм пока не обслуживает.

Ключ включает SHA256 исходников исполнителя и профиля, всех объявленных входов,
идентичность предшественников и их выходов, абсолютный путь репозитория,
версию/платформу Python, хеши его интерпретатора, стандартных Python-исходников,
extension-модулей и DLL, а также хеш окружения. Значения окружения в отчёт
не выводятся. `PYTHONOPTIMIZE` удалён, чтобы не отключать `assert` существующих
аудиторов. Чтение старого локального `.pyc` исключено отдельным новым путём
pycache для каждого выполняемого шага.

Перед cache hit проверяются хеши сохранённых артефактов и лога. Исходные
артефакты остаются по прежним адресам: их удаление или повреждение вызывает
новый запуск. Исполнитель не копирует старый отчёт в новый каталог под видом
свежего исполнения: `report.json` явно содержит `cached` и исходные пути.
Не переносите каталог кэша как независимый архив без связанных артефактов.

Проверяются входы до/после шага и снова в конце прогона; профиль, исполнитель и
Python также повторно сверяются в конце. Новые cache receipts публикуются только
после успешного завершения всего набора. Ошибка останавливает следующие шаги;
при таймауте завершается дерево процессов (`taskkill /T /F` на Windows или группа
процессов на Unix). Проверки последовательные, чтобы не создавать конкурирующие
нагрузки на машине пользователя. Отчёт сохраняет длительность каждого шага,
общую длительность, exit code, таймаут, хеши и пути результатов.

Это локальный доверенный кэш, а не доказательство независимости или sandbox.
Скрытые импорты, сторонние пакеты, системные shared libraries и внешние файлы
автоматически не устанавливаются как полная closure. Для такого шага оставьте
`cache=false`, пока не проверены все входы; после изменения системной среды,
не покрытой ключом, используйте новый cache или `--no-cache`. PDB/source gates,
тесты сборок, оригинальные captures и релизные проверки не заменены и не
отключены.

Локальная проверка 28 октября 2026: десять тестов исполнителя прошли. Они
запускают реальные дочерние Python-процессы и проверяют cache hit, изменение
входов/аргументов/окружения/runtime, glob membership, повреждение/удаление
артефактов и JSON, ошибки, отсутствие выхода, таймаут, циклы, порядок
зависимостей, остановку после ошибки, изменения входов во время проверки,
запрет отключения assert, изменение артефактов предшественника последующим
шагом и отсутствие нового кэша при неполном прогоне.
В этих unit-тестах fingerprint Python заменён маленькой fixture; реальные
два запуска профиля использовали полный fingerprint без замены.

Для двух шагов начального профиля в финальном прогоне измерено **1,67 с** на холодном запуске и
**0,72 с** на повторном (оба шага `cached`). Это около 2,3 раза для данного
короткого прогона на этой машине. Эти числа не распространяются на сборки,
инференс, полный движок или длительность самого переноса.
