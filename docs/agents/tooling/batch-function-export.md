# Пакетный экспорт функций для переноса

`tools/handwriting/export_port_batch.py` собирает функции одним headless-сеансом
существующего проекта Ghidra. Он не запускает анализируемую программу, не
создаёт функции и не сохраняет изменения проекта. Выгрузка включает C-псевдокод,
инструкции с исходными байтами и входящие/исходящие ссылки. Экспортёр общий:
привязки к конкретному движку или SDK в нём нет.

Это следующий инструмент после исполнителя проверок из 1.2.8. Тег 1.2.8 не
меняется; разработка ведётся для следующей версии.

## Запуск

Нужны установленная Ghidra, совместимый JDK и уже проанализированный локальный
проект. SDK, проекты и декомпиляция в Git не добавляются. Пример запроса:

```json
{
  "schema": 1,
  "binarySha256": "18f1b4fc211ae96cecd05611f72dbef52d93ac4484c61b735c8296dc01c3977f",
  "addresses": ["0x180152280", "0x1801522f0", "0x1801fcf40", "0x1802144f0"],
  "decompileSeconds": 45
}
```

Пути в примере ниже соответствуют существующему локальному исследовательскому
проекту; для другого бинарника замените SHA256, адреса, проект и путь программы.
`--output` всегда должен быть новым каталогом.

```powershell
python -B tools/handwriting/export_port_batch.py `
  --request .artifacts/function-request.json `
  --binary research/myscript/sdk/build/x64/MyScriptText.dll `
  --ghidra-home research/myscript/tools/ghidra_12.1.4_PUBLIC `
  --java-home research/myscript/tools/jdk-25.0.4.1+1 `
  --project-dir research/myscript/ghidra-projects `
  --project MyScriptText --program MyScriptText.dll `
  --output .artifacts/function-export-001 --timeout 180
```

Адреса приводятся к одному формату, сортируются и дедуплицируются перед запуском.
Каждая точка обязана быть существующим entry point. Для адреса внутри функции
отчёт показывает содержащую функцию, но не подменяет им запрос и не меняет базу.
При неполной выгрузке процесс Python завершается с ошибкой даже тогда, когда
сама Ghidra вернула 0. Частичные файлы сохраняются для диагностики.

## Что проверяется

- SHA256 файла совпадает с запросом и SHA256 программы, записанным в проекте.
- Headless работает с `-readOnly -noanalysis`; до/после проверяются хеши `.gpr`
  и содержимого `.rep` без временных lock-файлов.
- Один сеанс обслуживает весь пакет. Heap ограничен 2 GiB, CPU — двумя ядрами;
  общий таймаут завершается вместе с деревом процессов.
- Java запускается напрямую без shell с VM-аргументами штатного LaunchSupport.
  Наследуемые переменные инъекции JVM-аргументов удаляются.
- Сохраняются хеши Ghidra/JDK, экспортирующего Java-скрипта, обёртки, process
  helper, запроса и бинарника; после выполнения входы повторно сверяются.
- Проверяются полнота списка функций, успешная декомпиляция и хеши каждого
  выходного файла. Отдельный PE-reader сверяет **каждый экспортированный байт
  инструкции** с исходным бинарником, независимо от декомпилятора.

В текущей версии независимая проверка байтов поддерживает только PE32+ с
исходной image base. Rebased-проект, ELF и Mach-O отказываются явно; расширять
поддержку нужно отдельными проверяемыми reader-ами. Отдельные символы данных,
косвенные вызовы и полнота графа исполнения из references не восстанавливаются.
Сверка байтов не доказывает правильность декомпилированных типов и алгоритмов.

## Повторная проверка без Ghidra

```powershell
python -B tools/handwriting/export_port_batch.py --verify-only `
  --request .artifacts/function-request.json `
  --binary research/myscript/sdk/build/x64/MyScriptText.dll `
  --program MyScriptText.dll --output .artifacts/function-export-001
```

Такой запуск не создаёт и не перезаписывает отчёт. Он проверяет сохранённые
файлы и исходные PE-байты. Это проверка выгрузки, а не повторная декомпиляция
или подтверждение актуальности проекта. Кэш Ghidra-выгрузок пока не используется:
состояние типов и анализа в проекте может изменяться при неизменном бинарнике.

## Фактическая проверка 28 октября 2026

На локальных Ghidra 12.1.4 и JDK 25.0.4.1 четыре существующие функции выгружены
за один сеанс за 16,83 с. Все **1825 инструкций** сверены с исходным PE; хеши
проекта до/после совпали. Это время конкретного пакета, не коэффициент ускорения
всего переноса и не показатель качества распознавания.

Промежуточный запрос из четырёх адресов обнаружил один отсутствующий entry point
`0x1801a7920` и был корректно отклонён; три успешные функции не превратили его в
успешный пакет. Этот результат сохранён отдельно, а не перезаписан успешным.
Отдельный отрицательный реальный прогон с адресом `0x180152281` внутри функции
также отклонён, указал содержащий entry `0x180152280` и подтвердил неизменность
проекта и входов.

Шесть stdlib-тестов проверяют полный/неполный пакет, дубли, неправильную
идентичность, подмену и отсутствие артефактов, изменённые инструкции с заново
вычисленным хешем, количество строк, границы секций и некорректные запросы.
Они включены в явный профиль проверок. Workflow `Recognition port tools`
запускает инструменты на Windows и Linux без Ghidra и SDK; реальные статические
экспорты остаются отдельными локальными проверками.
