# Older structured Math search: positive caller and configuration boundary

This is a static boundary proof, not a runtime port or a font-sizing model. It follows the previously exported Math 0695E0 / 06ADC0 / 06BBC0 callers into the actual MyScript2D 1F45 processor. The new audit checks eighteen complete contiguous Ghidra bodies, 1,937 instruction locations and five class/method data regions, then composes the typed-storage, public-builder and modern/typed representation evidence. The vendor DLLs were never loaded or executed.

The useful result is a positive older search entry and its configuration/typed-DOM feeder. Its search callees, resource payloads and final typed-result producer are not yet closed. No raw EE4-to-138D conversion, inferred confidence, font estimate or application admission follows from this batch.

## A concrete search call, not an inferred layout callback

MyScriptMath 06BBC0 operates on the actual `mathField` owner and selected source. It obtains DAF source state, resolves or reuses a retained worker through CBD, derives source selections and updates existing result state through 06ADC0. When a new search is needed, it populates worker input through 0689F0 or the reuse/incremental helpers, handles source gaps through 06B670, and may feed an existing `mathResult` terminal/nonterminal tree through 0695E0. The operation checks the real processor fields +380 and +388 before invoking the base 1F45 service's V20. These fields are not proved font resources by their offsets or by this caller.

The owner distinction is essential: 06BBC0 passes the **outer processor** as argument two to 1F45 V20, and the separate **input/result worker** as argument three. Thus 009500 parameter two owns the configured resources and search buffers; parameter three supplies the request counts and constraints. The CBD-created object and the 1F45 processor are not interchangeable owners.

The 1F45 descriptor and actual primary method table reside in MyScript2D. Primary 088278 +20 is exactly 009500; +28 is the configuration method 0065A0. This makes the 06BBC0 call into a real native search body concrete. It is not a guessed callback name. After that call succeeds, 06BBC0 obtains the actual worker result through interface 13EC and routes it to the actual later result-publication service. The existing typed writers and owner lifetimes remain necessary; this proof does not replace them with a prepared list of tags.

The newer Document 028070 sequence producer is a separate positive route. It supplies first-AL text and fallback DOM. A fallback terminal existing under a newer result is not proof that the older worker consumed EE4 labels as grammar tokens. At most it provides an existing DOM structure to the feeder when that caller actually selects the older route. Whether the real application configuration invokes this older search after modern recognition remains a separate dispatcher/provenance question.

## Actual configured owners

1F45 processor constructor 005C00 initializes its owned working buffers and clears the configured owner fields. The complete 0065A0 method accepts objects derived from actual types 1F47, 13EA or 1F48, rather than an arbitrary caller string or native address. It retains/replaces 1F47 at +130, retains/replaces 13EA at +180, and retains/replaces 1F48 at +188. The latter also refreshes a derived service at +190. Changing relevant owners marks the processor state dirty. Replacement releases the previous owned reference; failure prefixes must not be called transactional rollback.

0068C0 removes an actual configured owner only when identity matches. 0069C0 returns configured state by the actual requested branch. 006E20 releases working search allocations. 006A40 prepares working state from the supplied request, including its arrays/counters; it is not a public adapter accepting an independent BlurMask stroke owner. Their exact bodies are pinned as part of this boundary.

009500 refuses when required +130 or +188 is null. The accepting types of those fields are proved by 0065A0. Their human-readable model names, serialized resource formats and exact association with the repository's existing `.res` files are **not** established here. Calling them a symbol classifier, spatial grammar or font model solely from their positions would overstate the proof. The optional 13EA attachment is likewise not silently treated as a required resource or as a replacement for either required owner.

## Search-entry branches and failure prefixes

The complete 7,759-byte 009500 body first handles an empty request (the two counts at request +2C and +78 are both zero). It rejects their unsigned combined count above 500 using native error code 03010000. These are native request fields; this batch does not reinterpret them as an arbitrary count of BlurMask strokes, points or tokens.

The nonempty path initializes working/candidate structures and bitsets, uses the configured owners and their derived services, and calls 008F80 and 007E50. The latter has ordinary and progress-callback paths, with 0074F0 as the native progress bridge. The caller observes returned statuses. Allocation and partial-working-state failures can occur before search completion, so an independently owned library entry would need whole-request budgets, cancellation and explicit prefix cleanup. No such runtime entry is introduced here.

The bodies of 008F80, 007E50, 0074F0 and their candidate-production callees are **not** included in this milestone. Pinning the complete entry establishes the real branches and call edges, not recovery of the entire search algorithm. In particular this batch does not claim that actual 1F44 candidate arrays have been produced by an independent implementation.

## Existing tree and geometry populate the separate input/result worker

Math 0695E0 branches on the actual existing DOM node kinds: rule, table, nonterminal, cell, border and terminal. It reads actual names/selected indices/ranges, table coordinates and border positions, traverses the actual selected children and calls the retained worker's typed operations. Its terminal path includes the actual source/segment data and later helper calls. Those values are supplied structural constraints, not a learned reconstruction of missing names from first-AL C-strings.

06ADC0 compares/reuses actual existing result selections and transforms. Its float/double operations and geometric tests do not, by themselves, establish font size or baseline estimation. 002A90 decodes an existing DOM numeric/range value representation; the 068CF0, 0690A0 and 0692B0 helpers carry the source/tree geometry paths. 0689F0, 068AC0, 06B670 and 06B7C0 support source loading/reuse and indexed working structures. Their complete bodies are pinned, but their downstream worker-interface implementations and all source-codec admission rules remain to be closed.

These routines must therefore not be described as an implemented native font-size model. Display-font metrics and selection of a replacement typeface remain a different analysis task. Neither the existing Math DOM visitor nor a copied bounding box proves that rendered text has the intended baseline/height in the application.

It also needs the actual source loader behind the feeder and the exact request-to-original-stroke/range mapping.
