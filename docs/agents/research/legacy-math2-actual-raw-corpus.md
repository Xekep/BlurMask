# Actual raw mathematical expressions, not only ownership fixtures

This separate headless diagnostic runs 31 raw coordinate inputs through actual
CPU ONNX inference, initial/final native-derived ordering, EF4, full EE4,
source attachment, selected-field copy and the fresh bounded publisher. All
93 runs complete the publisher. Cold/default width1 and explicitly diagnostic
prepared widths3/16 remain separate policies. No secondary candidate is selected
by an expected label; record zero is the actual selected first output.

The input set is 17 fixed procedural polygonal samples and the existing private
14-sample audit corpus: 13 human MathWriting expressions and the official
Android quadratic example. The procedural generator declares its coordinates
and labels before inference; it is not handwriting, training data or an accuracy
benchmark. The existing corpus provenance, pinned archive and research-only
data license are documented in `math-ocr-corpus-audit.md`. Licensed coordinates
remain in private artifacts and are not added to application assets.

The probe supplies only coordinates to inference. It reads expected labels after
all three runs for an input. It records each actual UTF8 alternative and actual
unit ID, score bits, feature bits, attention frame hashes and resulting fallback
publisher names. Failures have an explicit stage/type/message; there is no
easier-candidate fallback. All 620 formatted records have an independent exact
AL-byte check; independent source geometry reproduces feature bits with zero
maximum error. Release Managed and Windows NativeAOT captures are byte-identical.

## What the actual selected first outputs establish

Cold width1 recognizes procedural digits0–9, plus and equals. It emits `1+2=`
and structural tokens for a raised2, integral limits, human fractions, matrices
and limits. The first integral without an equals emits
`<underover>∫<underover2>1<underover3>10</underover>X<sup>2</sup>dX`.
These are actual NN/EE4 outputs, not a claim that a semantic terminal tree or a
native evaluator has been restored.

A **named diagnostic library adapter** calls the existing `MathLatexFormatter`,
`NumericExpressionEvaluator` and `PolynomialIntegralSolver` on these produced
tokens. It does not change any production API or app dispatch. The actual first
output without equals formats as `\int _{1}^{10}X^{2}dX`; the existing polynomial
solver independently returns333, but the diagnostic equals-gated result stays
null. The same procedural integral with a final equals recognizes
`\int _{1}^{10}x^{2}dx=` and produces333. Similarly `1+2` has no requested result,
whereas `1+2=` produces3. All three width policies exhibit those first-record
results. UppercaseX is preserved; the lowercase secondary from a different run
is never substituted using the expected answer.

The independent oracle recomputes finite polynomial answers as exact rational
arithmetic from actual recognized syntax, verifies the equals gate and checks
both captures. It does not claim to independently reimplement the complete
LaTeX formatter, calibrate NN confidence, prove all mathematical recognition or
reproduce the native semantic evaluator. Misrecognized alternatives remain in
the capture, including wrong symbols and bounds.

## Reproduction

Generate procedural ink with
`python tools/LegacyMathActualCorpus.Probe/generate_procedural.py <private-output>`.
Build the separate probe; pass its arguments in order: model pack, rawMath2,
official Microsoft CPU ONNX Runtime, output JSON, procedural manifest and the
existing private corpus manifest. Audit using
`python -I tools/LegacyMathActualCorpus.Probe/audit_output.py <capture> <rawMath2> [native-capture]`.
No vendor DLL is executed or loaded. The project reuses the existing diagnostic
friend assembly name in its own output directory and changes no old file.

## Remaining integration boundaries

The NN already emits a nontrivial 2D token language. The bounded publisher still
constructs the proven fallback sequence/`char=?`/empty `mathTerminalNode.name`
schema. That is not a completed structural math tree or solver acceptance.
Native terminal/tree expansion and original CBB/revision/observer ownership
remain independent tasks. A library adapter from actual owned first-record
tokens to a strict structural representation and existing solver is a possible
explicit implementation route, rather than claiming native equivalence.

Existing app routing uses a confidence threshold from its older greedy model.
The new source score bits are ranking scores, not a calibrated probability.
No confidence1, copied greedy confidence, implicit acceptance or app recognizer
switch is introduced by this diagnostic. An experimental production adapter
needs an explicit result/ownership/cancellation/budget API and an honest
confidence/acceptance policy before any old application seam is changed.

CI generates only the17 procedural inputs and runs both Managed/NativeAOT
with `--procedural-only` on the independent oracle. The31-input private corpus
remains a separate explicit local check; licensed human inputs are not fetched
or included by this CI step. Neither scope is an accuracy benchmark.

## Calculation update,28 October2026

The earlier numeric/polynomial solver observations above are historical. Both
custom evaluators have been removed. Current diagnostic probes produce only
`diagnosticGiac`/`diagnosticEqualsGatedResult`, invoking Giac solely for a trailing
equals and only when `BLURMASK_TEST_GIAC` explicitly supplies its CLI path. With
no Giac path there is no computed diagnostic answer. Recognition data and
expected-label separation are unchanged.
