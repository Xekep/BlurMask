# Fresh Math transfer from the completed temporary field

This is a static checkpoint after the completed fresh Math publisher. It adds
no runtime API, application switch, native edit ABI or page acceptance. Vendor
DLLs are read as bytes only. The new auditor pins 27 contiguous Ghidra function
bodies, verifies exact byte hashes and complete linear decode through each end,
and checks 3290 addressed instructions plus 15 dispatch bindings. Two complete
iterator leaves absent from the Ghidra function export and one focused constructor
branch have separately labelled extents. These are
body extents, not the first PE unwind fragments. The existing temporary-patch
and original-source-history proof trees also pass independently.

## Four document owners, three registry owners

The input to Document028070 is the worker-selected BCD, its selected Ink and
the pending receiver. Document00D540 obtains the original page receiver through
the request reader.V200 and asks it for original Ink/DOM through V78. It creates
two separate worker pairs. Each Ink comes from original.V170 with final flag1,
so history is disabled; each selected DOM clones the actual requested field
through 00C590. The original registry, chosen worker registry and third registry
used during publication are distinct. Their corresponding INPUT C22s have
separate owner identities even when their ranges and registry ID are equal.

The publisher's temporary BCC contains a clone of the actual selected mathField
under a generic root. Its candidate BCC has the same selected name owner but
separate nodes. Its three candidate payload subtrees are cloned into that
temporary arena before its internal patch is applied. Late pending resolution
registers on the third Ink, rewrites tags on the actual inserted temporary
nodes and preserves the selected INPUT ID/Next provenance.

The outgoing DOM edit introduces a **fourth BCC**. Selected DOM.V208 dispatches
Engine0EFA00 to BE2.service0=0E3A70. This constructs a fresh BCC writer and calls
0E2250 with that writer as its seventh argument. The old root is the actual
selected field and the new root is the completed temporary field. This is
different from the earlier CB8.V10 call, whose optional writer is null and
whose old root is the temporary mathResult.

0E2250 checks that the old field belongs to the selected reader and that the
node kinds agree. It retains the fourth writer and builds a new action batch.
0E35C0 converts that batch into a 24-byte exported edit with 40-byte rows. Each
row carries opcode, path storage/count, ordinal and cloned payload. Its path
walk stops at the actual selected field root, not at PAGE/content or a generic
library root. Payloads are deep-cloned through the fourth writer.V88. The
returned edit retains that writer. The source temporary tree can therefore
be released after successful export; a borrowed node snapshot cannot replace
this owning transfer.

The fresh selected field has its original id attribute and INPUT subtree.
Its completed temporary clone adds one mathResult after INPUT. Therefore the
outgoing fresh-field difference must compare those preserved nodes and emit
the added mathResult as its one subtree insertion; it must not export the
three earlier candidate-child actions. The default matcher has a fast equal
prefix path (0D33F0→0D4C10). Element scoring is 0D4810: equal name owners permit
pointer comparison of canonical names, unequal owners compare strings; absent
matching rules yield zero for equal element names. A nondefault attached
matcher or rule set remains outside this fresh bounded proposal. This static
checkpoint pins the scoring bodies. The separate reduction checker consumes all
six actual frozen publisher outputs, verifies the retained nonempty INPUT/id
prefix and produces the one field-relative row. It deep-copies the full typed
mathResult subtree with source-node mapping and attributes before children. This
is a prepared oracle for the proposed bounded transfer, not a produced outgoing
runtime edit or a general matching implementation.

## Source command export follows DOM export

02896D invoke selected Ink.V178 with selectors(-1,-1) and the exact third Ink.
Ink06EBE0 resolves C4D.service28=07DB60 and passes ignoreAuxiliary=true.
07DB60 constructs a new 40-byte C4D transaction and invokes 07BA80 using the
selected Ink as old state and third Ink as new state. Raw/current differences
are considered before 07AE90 compares the registries.

07AE90 obtains both registry ID sets, computes new-only, old-only and common
sets, then emits additions, deletions and changes respectively. Additions use
07A5B0: opcode4, explicit ID at18, interned name20, ownsRanges28=1, detached
C22 at30, auxiliary38, category40. The command C22 is constructed with null
Ink owner and a copy of the actual new entry's ranges; it is not the retained
third C22. With ignoreAuxiliary=true, auxiliary38 stays null. Existing equal
entries produce no command. The final operation7 is appended only when old
Next is less than new Next; oldCounter is20 and newCounter18.

For this publisher raw/current data is shared unchanged, old INPUT0 is unchanged,
new MATH_SYMBOL/MATH_NODE entries have category102 and IDs from actual selected
Next, and Next increases accordingly. This establishes the intended new-only
branch and trailing counter. Ink001910's default branch at001F57..002015 installs
descriptor0F50D0+20=0F5120 into Ink-context20+40. This service's insertion70 is
0B70A0: signed-key comparison builds an ordered tree. Difference48=0B81D0 and
intersection38=0B7C50 produce sets. Iterator58=0B7690 descends to the leftmost
key; next60=0B76E0 follows the right subtree and its left descendants, then
unwinds the saved ancestry stack. Thus new-only additions are exported in
ascending actual ID order. This differs from assuming arbitrary dictionary or
pending enumeration. The prepared reduction checker explicitly sorts the actual
produced registry IDs, verifies INPUT equality, new categories/ranges and exact
rewritten DOM tags, and emits the trailing actual counter pair. Four altered
provenance controls refuse. The runtime outgoing transfer is still unimplemented.

## Pending receiver transfer and failure prefixes

028980..0289A2 calls actual pending receiver.V18 with row
`before=-1, after=-1, forwardDOM=exportedEdit, reverseDOM=null, Ink=exportedC4D`.
Document11B860 grows the actual row vector, zeros the new row, increments count
and writes these five values. It does not retain or clone the supplied edit
pointers. A row-growth allocation failure returns false before row insertion.

Native028991 sets its success byte **before** the call and 0289A5 jumps directly
to cleanup without testing its return. Thus a successful publisher return is
not proof that the pending receiver actually accepted the row. There is also
no local release of an already exported DOM edit when the subsequent Ink diff
returns null. This checkpoint reports that incomplete failure prefix rather
than describing the native transfer as atomic or inventing rollback.

The owning C8F destructor11B6C0 and row-removal11B950 release forward/reverse
BE2 edits and C4D transactions only when its owning flag20.bit0 is set. Successful
row insertion into such a receiver transfers ownership; failure cannot be
described as a completed handoff. C8F.V10=11BAA0 separately resolves its weak
C8E callback and dispatches C8E.V70=00F110. Its bit1 early return is a different
condition from the owning bit0.

## Original selected/page target and source history remain explicit

00F110 obtains the original page Ink/DOM from the receiver, resolves the incoming
sourceName28 exactly once in that original DOM, reconstructs the actual BCD,
and verifies the existing field state's revision48 against incoming revision30.
The Math INPUT tag, new result tag and source-name string are separate domains.
Document115800 reads original inner38 Ink and inner30 DOM, queries the exact
sourceName to one actual original field, then preflights Ink.V180 and DOM.V210.
On the accepted branch it applies **original Ink.V188 before original DOM.V218**.
DOM.V218 receives the actual field query result, not the original PAGE root.
Page/CB7 begin/end and the shared original C81 history lifetime surround this
process; failed source application or DOM application enters their real rollback
path. This is not authorization to apply directly to a caller-supplied field.

Supplied category102, like100, is outside 10..12 in 13C610 and outside10/12/11
in 13B240: it does not require those geometry callbacks and is classified as
ordinary. This follows from actual Math category bytes, not Text receipt type
coercion. Original registration still invokes the original observers and journal.
The existing source-history proof establishes that observer allocation failure
can leave registration successful with an incomplete generated inverse journal.
Undo walks generated records backwards and need not restore the initial Next.
Those distinctions remain necessary for a Math-specific owning application.

## Proposed next bounded library join, not implemented here

The nonempty-prefix, concrete ordered-ID and field-relative row reductions now
have static byte evidence and six prepared actual-output controls. Next add
NEW Math transfer owner/kernel/probe/oracle files. The owner must consume one
actual completed publisher, own the fourth DOM arena and detached command C22s,
retain original/selected/third identity maps, validate all IDs/ranges/categories,
preflight payload budget before clones, and expose entered failure prefixes.
Keep typed Text receipts and prepared Text selection commands unchanged.

The minimal old seams would be one read-only trusted completed-publication
accessor under the publisher gate, and one new Math-specific original-field
application accessor under the actual original source gate. Never acquire an
outer receipt gate while holding either gate. Claim once on the actual produced
publisher outside its gate; recheck active source/receipt identities before each
mutation boundary. The source-only journal can be a NEW Math adaptation of the
proved neutral algorithms, with explicit generated-journal completeness.

Only after that owning transfer is tested should a separate original-field DOM
application/journal join be authorized. It must insert the actual exported
mathResult under the existing original mathField after successful source replay,
preserve existing id/INPUT/PAGE nodes, map canonical names into the original name
owner, and retain independent history/failure diagnostics. Full native CBB cache,
revision, store, asynchronous callbacks, observer ABI, shared Base70 page frames
and arbitrary prior-result replacement are not supplied by the bounded join.
