# Public MathResultBuilder and the typed-result consumer

This followup closes a positive public-API-to-DOM construction chain. It does not recover a neural grammar or establish a raw EE4-to-legacy-object conversion. There are no runtime or application changes. The audit pins 24 complete contiguous Ghidra bodies, three exact standalone return leaves, 1,451 instruction locations, three literals and five data regions across Document, Math and 2D. It composes `audit_math2_document_route_boundary.py`, which in turn checks the seventeen-body typed Math exporter boundary. The three return leaves are expressly not called full Ghidra functions.

## The supplied-text builder has a real, checked caller

Document 08C260 obtains the engine context and resolves the supplied object handle. It verifies derivation from ED9 or reports `target is not a MathResultBuilder`. An empty supplied text-length argument is refused. Before using text, it resolves the supplied source selection with 08A910 against the builder's retained document and ink owners. A page selection must belong to the same page; a C23 selection must belong to the same ink. Their explicit failure messages are pinned. The wrapper then converts the supplied text into a temporary string buffer and calls the builder's V C0. The temporary buffer is freed on both success and failure.

The actual ED9 primary method table is at 2084B0. Its V C0 slot is the exact pointer 10BA10; V B8 is 10B8E0. These offsets are asserted from the real binary, rather than inferred from adjacent decompilation. 10BA10 is the previously proved complete one-terminal producer: events START_TERMINAL, START_TERMINAL_CANDIDATE, CHAR, END_TERMINAL_CANDIDATE, END_TERMINAL. Its CHAR record owns a retained supplied selection. Together with EDA reduction 4 and CB8 finalization, this is a concrete path from **caller-supplied text plus source selection to an actual named terminal and produced document edits**. It is not automatic recognition of a fraction/exponent from those characters.

Document 08C020 is the lower-level CHAR wrapper. It applies the same ED9/selection validation, converts supplied text, obtains a separate retained selection copy, then calls V B8 / 10B8E0. 10B8E0 interns the supplied string, retains the supplied selection in event kind 7 and submits it to parser V68. If submission returns -1, it releases the selection payload and frees the rejected event. The public wrapper separately releases its temporary selection reference and string buffer. This distinction prevents treating one borrowed public selection as an unowned parser payload.

08ACE0 supplies a converted string and integer to V28 / 10A9B0, which emits START_RULE event kind 8 and stores the supplied integer. This is another explicit public event, not an inferred vocabulary-to-rule mapping. 08AB00 returns the builder's owning document through V10 / exact leaf 0A5280, which reads the actual retained owner at +20. 08C440 validates the supplied result object's BCD derivation and C98 kind 2 before forwarding it to completion V D0; a null result argument is separately accepted for that call. It must not be widened to accept any arbitrary node or unvalidated recognizer output.

## Registration and construction are distinct from the public text calls

The SDK's named PE export `MyScriptDocument` is **module descriptor data at 1B5F50**, not executable code. Its +18 pointer selects module registration function 001470. That complete function passes the actual ED9 descriptor 208450 and EDA descriptor 208BD0 through the registration callback and checks callback failures. No vendor code was executed to obtain this evidence.

ED9's registered owner metadata 208418 points to the actual primary table 2084B0. Its constructor callback at 2084A8 is 10A5A0, whose constructor arguments/owned CB8/parser/document/string owner were proved in the prior batch. The exact size leaf 0D9D50 is only `mov eax,0x60; ret`; the exact predicate leaf 10C130 tests the supplied integer against E75 and returns a Boolean. Those leaves are pinned separately and are not assumed to implement generic engine allocation, a factory that recognizes strokes, or a parser.

The public wrappers in this batch operate on an already resolved ED9 handle. The generic external object-allocation/constructor caller is not newly recovered here. Registered metadata and a checked constructor are real construction evidence, but do not justify inventing an application creation call or claiming every engine constructor failure has been transferred.

## Existing modern and typed Math results share a consumer dispatcher

Document 05A3C0 is a bounded existing-result consumer owner constructor accepting a 0x28-byte parameter structure. It retains actual owners, constructs source/selection state, obtains the current result via C98 and branches on the actual returned content kind. For kind 2, it checks the existing result marker byte at result+18 → +30 → +4 against `'R'`. The modern DOM branch calls 059F70 with the existing document/node. The alternative branch recursively visits actual typed objects through 0590C0. This is a positive distinction in a common consumer, not a guess that every mathematical object has the same storage layout.

0590C0 dispatches the actual registered type ID minus 138D. Terminal 138D enters 058420; nonterminal-style cases use 058E70, which queries actual interface 13F1, reads its selected child and recursively visits that child. Rule/table-style cases query 13F2 and visit real children while preserving the traversal prefix. The unsupported 1390 branch refuses. This recursion must not be replaced by flattening all child names or selecting whichever child matches an expected answer.

058420 requires C5C source identity, an existing registry selection and intersection with the retained selection. It obtains the actual object's 13F0 interface, reads the selected index through +30, obtains its symbol count through +40, and iterates those symbols. The name/reference string comes from actual +68. A leading byte 3 triggers the existing document reference/tag lookup; otherwise the subsequent +50 path produces the real character data into the owner's buffer. Its multi-character check rejects data that does not decode to the required single-character unit. Existing source ranges and further candidate/document operations are preserved by this function. No AL alternative C-string is supplied to these calls. Thus a missing fallback name is not evidence that looking up a 138D interface on a modern `symbol` string would be legal.

059F70 instead operates on an existing DOM `mathTerminalNode` and its tags/ref, source symbol ranges, `sequence` or existing segment/candidate representation. That path updates existing source-related content; it is not an inverse factory creating registered 138D objects from EE4 labels.

## Where the old typed objects actually originate remains open

The Math 138D **class** descriptor at 09A880 derives from actual base type 1F44. That base class descriptor is positively present in **MyScript2D.dll at 088130**, derived from 1F41. It is not defined by the Math 13F0 public callback table. This provides a concrete next ownership lead into the separate 2D object implementation; it does not prove a link to the newer raw EE4 route.

The Math descriptor at 09AA80 registers public callbacks for interface 13F0. Its callbacks 0425B0 through 042F50 resolve handles and query the object's actual 13F0 interface before forwarding operations, performing index/buffer checks and converting output for the public ABI. Their table is **not** the native object's interface implementation table. In particular its adjacent callback positions cannot be relabelled as native V50/V68 implementations. 040C80 likewise delegates the actual class destructor to its base. This distinction is material: otherwise a list of public wrappers could be mistaken for a recovered recognizer or grammar evaluator.

The exact base implementation, generic allocation caller, all native typed-event productions and any indirect bridge from newer sequence output remain unclosed. The existing cold neural output already carries useful structural markup. The independent strict structural adapter consumes that actual markup explicitly as library glue, without claiming that it recovered these old 2D typed object constructors or their confidence policy. No app/default switch, Russian recognition completion, evaluator or engine-completion percentage is authorized by this static result.
